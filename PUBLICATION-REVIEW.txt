Weekly contract and failure behavior
- weekly and weekly_summary share one key:
  weekly:ALL:<recommendation-week-Monday>:<Friday>:<evaluation-Friday>.
  KR/US rankings remain separate inside the existing combined weekly report.
  The original Mon-Fri cohort, first recorded recommendation price, 14 days
  after that Friday, previous market session on holidays, and Saturday 17:00
  KST publication policy are unchanged. US row session dates win over archive
  filename dates. No current news/fundamentals or current-price substitution.
- After the existing publisher concurrency slot is verified, reread main.
  Commit and confirm collecting before historical quote work. Commit frozen
  report, history_index.json and published ledger atomically; confirm all three
  before a durable notification claim and existing Expo recipient lookup.
- A published period with matching output hash and its index entry is a no-op:
  no quote work, no new history/index/state writes, no recipient lookup/send.
  Later index entries do not invalidate old periods. Frozen output is immutable.
- Calendar/price fetch failure, unreadable archive and an unverified empty
  cohort do not publish a report/index or send a notice. Failed claims remain
  bounded diagnostics; existing successful files are preserved.
- Existing deterministic unavailable cases (missing/ambiguous entry price,
  unverified legacy price basis or corporate action status) remain unevaluated,
  with null return, original missing counts and dataStatus=partial in the
  ledger/result. Partial notices explicitly state unavailable records. Such a
  published partial report remains frozen; it is not silently recalculated.
- Existing legacy reports/index entries without a verified ledger are blocked
  for explicit adoption review, not overwritten or announced again. Failed or
  collecting claims are not stolen when the owner status is unknown; even a
  terminal owner needs separate recovery approval. Runtime retry_authorized
  stays false; there is no automatic force, replay, TTL takeover or retry CLI.
- Expo notificationKey is a stable weekly hash, not a provider exactly-once
  guarantee. Unknown response/crash after claim can leave omitted recipients;
  retries do not resend the whole audience. Accepted tickets are not device
  receipt confirmation. Tokens remain in memory, not public state/logs.
- Legacy pending-file push steps are removed from the proposed workflow to
  avoid a second send. Existing schedule, mode/target inputs and concurrency
  group remain unchanged. Manual legacy notify/update_index CLI functions are
  retained for compatibility but are not part of the guarded workflow and must
  not be used to bypass recovery review.

Stopping / rollback - requires operating approval
- OFF prevents future gated starts; it does not stop a job that already read
  its environment. Inspect active run state, never steal unknown ownership.
- Preserve scan_state.json, frozen reports, daily histories and history_index.
  Revert only reviewed code commits, keeping concurrent user/data changes.
  Reverting just this weekly delta restores PR #7's unguarded weekly path and
  can repeat notices; reverting PR #7 too restores unguarded daily behavior.
  Neither is safe to replay for already successful periods. Use a reviewed
  quiet window/new period and reconcile the recorded claims first.
- No code rollback can recall accepted notifications. An unknown notice is not
  authorization for another send. Failed-data recovery needs root-cause repair,
  output/owner inspection and a separately approved recovery implementation.

Limits
Only saved recommendation snapshots can be evaluated. Missing historical files
or overwritten same-day observations cannot be reconstructed by this guard.
It does not prove a complete historical recommendation population, adjusted
returns, profitability, live provider permissions or actual device delivery.
No new schedule, database, infrastructure, credential, IAM or paid plan is used.
