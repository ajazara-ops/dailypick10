Firebase 규칙 변경안 — 적용하지 않음 (2026-11-01)

대상과 확인 수준
운영 대상은 사용자가 지정한 프로젝트의 기본 데이터베이스 (default)이며 Spark를 유지한다.
실제 project ID와 서비스계정 이메일 및 진단 링크는 비공개 로컬 전달 문서에만 보존한다.
신원 일치는 로컬에서 확인했으나 이는 인증·권한 사용 검사가 아니다. 실제 키 유효성, 조건부 IAM/deny 정책, 런타임 권한은 미검증이다.
현재 규칙 근거는 사용자 제공 화면이며 current-rules.from-user-screenshot.txt에 보존했다. 적용 직전 실제 게시 규칙을 다시 대조해야 한다.
제안 전체 규칙: spark-intake.rules.example. 정확한 텍스트 차이: spark-intake.rules.diff.
기존 광범위 owner read/write와 병합하지 않고 검토된 전체 ruleset으로 교체하는 안이다. 현재는 파일 준비만 했다.

클라이언트 권한 변화
경로 | 현행 화면의 규칙 | 제안
users/{uid} | 본인 read/write | 차단 없는 본인의 get/create/일반 필드 update만. list/delete 금지. deletionRequest 변경은 신청 트랜잭션의 일치하는 requestId만 허용.
accountDeletionIntents/{uid} | 허용 규칙 없음 | 본인 get. 최근 인증 300초 안의 version 2 신청과 정확히 7일 기한 전 cancel_requested만. list/delete/서버 완료·취소 확정 상태 직접 쓰기 금지.
accountDeletionIntents/{uid}/attempts/{requestId} | 허용 규칙 없음 | 본인 get 및 신규 신청과 묶인 최초 create. update/list/delete 금지. 사용한 요청 ID 재사용 금지.
accountDeletionJobs/{id}, accountDeletionState/{uid}, accountDeletionReceipts/{id} | 허용 규칙 없음 | 계속 모든 클라이언트 read/write 금지. 서버 전용.
기타 경로 | 허용 규칙 없음 | 추가 개방 없음. 공개 비로그인 조회 경로·공개 암호문 영수증 없음.

시각·취소·차단
requestedAt/cancelRequestedAt은 Firestore request.time과 같아야 하며 auth_time은 인증 토큰과 묶는다.
클라이언트 UID·임의 기한·완료 상태를 신뢰하지 않는다. getAfter로 intent/attempt/프로필 표시를 함께 검사한다.
신청 즉시 일반 프로필 접근/재저장을 막고, 현 알림 코드가 읽는 deletionRequest 표시를 함께 남긴다.
취소는 서버 확인 전 차단을 유지한다. 확인 실패/응답 유실/오프라인을 취소 성공·삭제 완료로 바꾸지 않는다.
Auth 철회 즉시 접수 차단을 보장하지 않는다. 배치가 현재 Auth 상태를 확인하기 전에는 영구 삭제나 서비스 복구를 허용하지 않는다.
공개 추천 JSON 자체와 이미 발송 제공자에게 전달된 푸시는 이 규칙으로 회수하지 못한다. 운영의 발송 직전 권위 상태 조회는 아직 준비/검증이 필요하다.

삭제 범위와 잔존 기록
운영 연결을 별도 승인한 경우에만 신청 후 604800초가 지난 동일 작업의 Auth UID와 users/{uid} 루트 문서를 정리한다. 작업 시각은 더 늦어질 수 있다.
users 하위 컬렉션, 스토어/RevenueCat 구독, 로그/백업, 다른 컬렉션은 추정 삭제하지 않는다. 구독은 별도 해지다.
intents/attempts/jobs/state/private receipts는 재실행 방지·감사·차단용으로 남는다. 보존 기간/법적 예외는 미확정이며 TTL을 추가하지 않는다.
Auth 먼저 삭제 후 프로필 정리로 단계 진행한다. Auth 실패면 둘 다 남고, 프로필 실패면 Auth는 없으며 프로필/차단/작업이 남아 같은 단계만 재시도한다.
완료 기록 실패도 삭제 복구가 아니다. 기록이 확인되지 않으면 앱은 완료를 확정하지 않는다.
기한 전 유효 취소는 선점을 막으며 확인이 늦어도 원래 취소 시각으로 판단한다. 삭제 시작 후에는 취소/복구가 가능하다고 안내하지 않는다.

필요 권한 — 이번에 부여하거나 사용하지 않음
작업 신원 후보는 사용자와 확인한 기존 서비스계정이며 식별자는 이 공개 검토본에서 제외했다. 사용자 IAM 화면에는 토큰 생성자/Firebase 인증 관리자/Firebase Admin SDK 관리자 서비스 에이전트 역할이 있었다.
화면의 역할과 secret의 신원 일치는 확인했지만, 조건/유효 권한을 실제로 행사하지 않았다. 새 역할이 필요하다고 단정하거나 기존 권한을 삭제에 사용하지 않는다.
필요 API 권한 후보: firebaseauth.users.get/delete; datastore.databases.get; datastore.entities.get/list/create/update/delete.
최종 운영 쿼리/SDK 바인딩이 확정되면 필요한 메타데이터 권한과 인덱스만 다시 대조한다. Owner/Editor, 규칙/IAM 관리 권한, secret 조회 권한은 배치 실행에 요청하지 않는다.
Admin SDK는 Firestore Rules를 우회한다. IAM의 삭제권한은 코드의 문서 범위보다 넓을 수 있으므로 고정 project/database·경로 allowlist·UID 세대 확인·단일 선점·한도·실패 담당자가 필요하다.
운영 어댑터/서버 read_time/임대/최종 쿼리·인덱스/별도 일정이 아직 운영에 바인딩되지 않았다. 지금 이 규칙만 적용하면 완성된 삭제 서비스가 되는 것이 아니다.

중단 및 rollback
지금은 적용 전이므로 되돌릴 운영 변경이 없다. PR 닫기/로컬 패치 미적용으로 검토를 보류할 수 있다.
향후 적용 직전 기존 ruleset 전체와 버전, 대상 database, 앱 호환 상태를 보존한다. 먼저 합성 검증 및 별도 적용 승인을 받는다.
신청/처리가 한 건도 없을 때만 게시 전 상태 확인 후 기존 ruleset 복원을 검토한다. 위 스크린샷 사본을 최신 운영 백업으로 간주하지 않는다.
활성 요청이 있으면 새 신청·새 삭제 선점을 중단하고 취소 접수·조회·차단 기록을 보존한다. 기존 unrestricted owner write로 즉시 되돌리면 재생성/푸시 차단이 풀리므로 금지한다.
이미 Auth가 삭제된 사용자는 규칙 rollback으로 복구되지 않는다. 부분 실패 작업은 담당자가 동일 requestId/UID 세대를 확인하고 승인된 정리 단계만 재개한다.
규칙 변경은 구버전 앱의 직접 문서 삭제/쓰기와 충돌할 수 있다. Auth 자기계정 삭제 API는 Firestore 규칙으로 7일 지연시킬 수 없다. 앱/정책/개인정보·스토어 안내 전환 순서를 별도 승인해야 한다.

운영 전 승인 항목
이 규칙의 적용 대상·전체 diff, 기존 신원의 삭제 권한 사용 범위, 실제 삭제 효과를 포함한 서버/앱 배포·일정 활성화, 장애 담당자·기록 보존·사용자 안내.
Spark를 유지하고 Blaze/새 유료 서버/키 발급은 하지 않는다. 무료 할당량 소진과 처리 지연 가능성이 있어 무과금·항상 즉시 처리 보장은 하지 않는다.
